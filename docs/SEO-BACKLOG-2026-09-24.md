# Part B — 剩余优化空间

## B.0 归因前提（先看这个，否则会选错方向）

当前唯一的硬约束是：**索引数 35 天冻结在 25，25 个 URL 停在「已发现 - 尚未编入索引」，而「已抓取 - 未编入索引」= 0。**

这意味着：**Google 没有把抓取预算给我们。** 所以下面的优化项要按这个标准筛——「能不能让 Google 更愿意抓我们」。

- 提升**内容可判断性**的 → 有用（B1、B4、B5）
- 提升**点击率**的 → 有用（已有曝光的位置提升转化）
- 提升**信任信号**的 → 间接有用（B3、B6）
- **新增 URL 的** → 当前**有害或无效**（B8、B9、B10）
- **站外权威度** → **唯一能解冻索引的**

## B.4 时间信号不真实（新发现，可立即修）

**证据（实测）**

```js
// astro.config.mjs
const BUILD_DATE = new Date();
serialize(item) { return { ...item, lastmod: BUILD_DATE.toISOString(), ... } }
```

实测 `sitemap-0.xml` 中 **50 个 URL 的 `<lastmod>` 只有 1 个唯一值**——全部等于同一次构建时间。
`WebPage.dateModified` 用的是同一个 `buildDate()`。

**问题**：每次部署都声称**全站 50 个页面同时更新**。Google 官方说明是「lastmod 只有在一致且可验证准确时才被采信」。恒为构建时间的 sitemap 携带**零信息量**，最坏情况是被忽略甚至打折——而我们恰好正处在「希望 Google 认为内容有更新、值得重新抓取」的处境。

**优化方向（三选一，需你决策）**

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 按页面维护真实复审日期 | 在数据层加 `lastReviewed`，只在内容实际变更时更新 | 最准确，需长期维护纪律 |
| B. 从 git 提交日期推导 | 构建时读每个源文件的最后提交时间 | 自动，但动态路由下同源文件的多页会共享日期 |
| C. 直接移除 lastmod | 诚实地不给信号，让 Google 用自己的抓取数据判断 | 最省事，但丢掉一个（本可有效的）信号 |

**预期收益**：**中**。这是**唯一一条直接作用于「重新抓取」的站内杠杆**，与当前瓶颈同向。
**优先级：P1**｜**工作量：S–M**
**我为什么没有直接改**：需要真实的按页日期来源。若我编造日期，比现状更糟。请选一个方案。

**如果还能做两件站内事**：B.1（补厚度）+ B.4（修时间信号）。两者都不新增 URL，且都指向「让 Google 认为这些页面值得抓」。
